## 两处直接关系到 Quick Decision

**4.29.4 可以借鉴「标准消息链」。** 群聊唤醒将合成事件标成唤醒，绑定原群会话，限制事件为普通成员，并交给事件队列。4.29.4 的处理阶段会对这类唤醒运行主 Agent。相比直接组装 runner，这条路径可以沿用主会话的锁、压缩、历史和发送流程。它也会经过其他已启用的消息钩子。Quick Decision 如果采用这条路线，需要先让自己的消息监听跳过带标记的后台事件，再由请求钩子使用本轮已有的决策。要分别验证群聊和私聊的会话身份、其他插件的联动，以及生成期间新消息到达后的取消行为。「群聊唤醒」的发送入口会检查活动时间是否变化，但取消发送不能回滚主 Agent 已经保存的历史。[合成事件与权限](https://github.com/BA7LCY/astrbot_plugin_group_wakeup/blob/68bb378f1a8bae1243c1df529d9ac58f97bd2764/main.py#L181-L261) · [发送前检查](https://github.com/BA7LCY/astrbot_plugin_group_wakeup/blob/68bb378f1a8bae1243c1df529d9ac58f97bd2764/main.py#L889-L945) · [4.29.4 唤醒入口](https://github.com/AstrBotDevs/AstrBot/blob/v4.29.4/astrbot/core/pipeline/process_stage/stage.py#L64-L74) · [主 Agent 锁](https://github.com/AstrBotDevs/AstrBot/blob/v4.29.4/astrbot/core/pipeline/process_stage/method/agent_sub_stages/internal.py#L230-L246)

**沿用主 Agent 后，提示词放在哪仍然会影响缓存。** 群聊唤醒把带本轮时间、近期聊天的话题指令加入 system prompt，会使与普通请求的差异提早出现。Quick Decision 已经有把回答策略附在本轮用户输入末尾的临时提示机制，可以在主动回合复用。Spark 提供了复用主 Agent 生成的案例，但它从旧版配置入口取压缩参数，自行写入占位和正文。不能据此认定它沿用了目前的压缩设置，或持久化了 runner 压缩后的完整消息与工具记录。[群聊唤醒的提示构造和注入](https://github.com/BA7LCY/astrbot_plugin_group_wakeup/blob/68bb378f1a8bae1243c1df529d9ac58f97bd2764/main.py#L765-L822) · [本插件临时提示](../reply_generator.py#L33) · [Spark 压缩配置](https://github.com/gongzhudeng/astrbot_plugin_Spark/blob/2b9ff4a65bba7b7b47c3ec7912cf21ea12287378/core/agent_config.py#L35-L105) · [4.29.4 官方压缩配置](https://github.com/AstrBotDevs/AstrBot/blob/v4.29.4/astrbot/core/pipeline/process_stage/method/agent_sub_stages/internal.py#L83-L145)

新版优先验证已在 4.30.0-beta.1 核实的官方 `context.agent.run_turn`。对 4.29.4，如果主动回合也要跑官方压缩，可先验证后台事件入队。如果当前目标是用较小改动保护已有对话，又允许用户短时间内追问，可以参考 Private Companion。生成问候时只用有限的近期消息，把确认发出的内容单独保存，并在接下来的普通回复末尾附上少量临时内容。启用这条续接需要按当前会话隔离，并让旧内容在 `/new` 和 `/reset` 后失效。直接补写主会话也能让用户接着聊，4.29.4 的 `add_message_pair` 仍会先读再整份更新，需要处理和普通回复并发时的覆盖风险。[官方主动回合](https://github.com/AstrBotDevs/AstrBot/blob/v4.30.0-beta.1/docs/zh/dev/star/guides/ai/agent.md#L1-L22) · [4.29.4 写入接口](https://github.com/AstrBotDevs/AstrBot/blob/v4.29.4/astrbot/core/conversation_mgr.py#L355-L390)

建议先在测试会话里验证工具调用及结果仍配对，再测试超长历史的压缩、取消发送和分段失败时的行为，最后测主模型的缓存命中。源代码能确认请求和历史怎样处理，实际缓存命中率及 QQ 送达仍需运行验证。本次只添加了这份调研。
